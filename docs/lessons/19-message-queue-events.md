# Lesson 19：消息队列与事件驱动

## 学习目标

完成本课后，学习者应该能够：

- 消息队列用于解耦、削峰、异步和事件流，不是复杂度免费的工具。
- 大多数队列默认只能承诺 at-least-once，因此消费者必须幂等。
- 重试必须有上限、backoff 和 DLQ。
- 事件 schema 需要版本化和兼容策略。
- 使用工具和实验验证本课核心机制，而不是只停留在概念理解。
- 将本课机制转化为生产代码中的设计判断、排查路径和 review 标准。

1. 什么时候需要消息队列？

5. Outbox 如何保证事务与事件一致？

## 核心结论

- 消息队列用于解耦、削峰、异步和事件流，不是复杂度免费的工具。
- 大多数队列默认只能承诺 at-least-once，因此消费者必须幂等。
- 重试必须有上限、backoff 和 DLQ。
- 事件 schema 需要版本化和兼容策略。
- Outbox pattern 解决 DB 写入和事件发布的原子性问题。

## 设计哲学

Go 的很多机制都服务于工程协作：让控制流、数据流、错误流和资源生命周期尽量显式。

本课需要持续追问三件事：

1. 这个机制让代码更简单，还是只是让抽象更多？
2. 这个机制在小程序里看起来无所谓，在生产环境下会放大成什么问题？
3. 我们如何用工具验证自己的判断？

对于 `消息队列与事件驱动`，不要只记 API 或术语，而要理解它对以下方面的影响：

- 可读性
- 可测试性
- 性能
- 并发安全
- 故障隔离
- 可观测性

## 生产实践

- 轻量事件优先 NATS，高吞吐可回放日志流选择 Kafka。
- 消费者以业务唯一键去重。
- 不要无限 retry 毒消息。
- 事件 payload 不泄漏不必要内部结构。

生产环境下要额外关注：

- 失败路径是否显式。
- 资源生命周期是否可控。
- 是否存在隐式共享状态。
- 是否能通过日志、指标、trace 或 profile 定位问题。
- 是否有测试覆盖正常路径、边界路径和故障路径。

---

## 常见误区

- 把“能运行”误认为“生产可接受”。
- 在没有 benchmark/profile 证据时做性能判断。
- 用复杂抽象掩盖不清晰的边界。
- 忽略取消、超时、错误包装和资源释放。
- 只测试成功路径，不测试故障和并发路径。
